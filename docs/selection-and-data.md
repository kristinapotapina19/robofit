# Подбор решений, каталог и данные

## Алгоритм подбора (`backend/app/core/selection.py`)

Движок возвращает не список подошедших решений, а **всех кандидатов** каталога с вердиктом:

- **Подходит** — все правила выполнены;
- **Требует проверки** — ключевых данных нет или решение на пилоте; показывается с предупреждением;
- **Исключено** — ключевое ограничение делает применение невозможным; указана решающая причина.

Правила применяются по порядку, первое исключающее правило останавливает проверку:

| Правило | Условие | Если не выполнено |
|---|---|---|
| Тип объекта | сценарий решения относится к объекту | исключение |
| Операция | подтип решения выполняет выбранную операцию (список в профиле) | исключение |
| Статус | в эксплуатации / пилот / НИОКР | НИОКР — исключение, пилот — проверка |
| Грузоподъёмность | ≥ массы грузовой единицы объекта | меньше — исключение, нет данных — проверка |
| Проходимость | паспортный мин. проход ≤ прохода объекта, иначе ширина робота + 400 мм ≤ проход | исключение / проверка |
| Бюджет | цена одной единицы ≤ бюджета CAPEX | исключение |
| Цена | цена есть | проверка |
| Отрасль | отрасль решения совпадает с отраслью объекта | проверка переносимости |

Правило — это функция `(решение, контекст) → вердикт + формулировка`. Новое правило добавляется одной функцией в список `RULES`, ядро не меняется.

**Ранжирование объяснимо** (п. 3.4.5). Рейтинг — сумма четырёх взвешенных факторов, вклад каждого отдаётся в `score_breakdown` и виден на полосе рейтинга в интерфейсе:

| Фактор | Вес | Как считается |
|---|---|---|
| Цена единицы производительности | 40% | лучшая удельная стоимость (руб. на ед./ч) среди решений той же операции / удельная стоимость решения |
| Уровень готовности (УГТ) | 20% | УГТ / 9 |
| Кейсы внедрения | 20% | есть описанные кейсы — 1, нет — 0 |
| Полнота ТТХ | 20% | доля заполненных: грузоподъёмность, скорость, автономность, производительность |

Пользователь может вручную добавить в сравнение и в расчёт исключённое решение (п. 3.4.4). Расчёт выполнится, но в предупреждениях и рисках будет решающая причина исключения.

## Каталог

Иерархия (п. 3.3.1): отрасль → тип объекта → процесс (профиль операции) → тип решения (подтип) → продукт. Её отдаёт `/api/catalog/tree`, в интерфейсе — раздел «Каталог».

Карточка решения содержит группы характеристик из п. 3.3.7: идентификацию (производитель, название, тип, сценарии, страна, статус), технические данные (`specs`), экономику (цена, комментарий к цене), применимость (сценарии, объекты, кейсы) и качество данных (источник карточки, ссылка, дата, признак подтверждённости каждой ТТХ).

### Происхождение характеристик

| Источник | Признак | Где задаётся |
|---|---|---|
| Паспорт эталонной модели из документа организатора «Примеры решений» | `confirmed: true` | `data/raw/reference_specs.json` → `models` |
| Типовое значение подтипа | `confirmed: false`, «уточнить у вендора» | `reference_specs.json` → `subtype_defaults` |
| Извлечено из названия или описания каталога | `parsed_from_name` / `parsed_from_description` | регулярные выражения в `etl.py` |
| Открытый источник (сайт производителя или дистрибьютора) | ссылка и дата | `data/raw/open_sources.json` |
| Введено администратором | автор и дата | админка / `POST /api/admin/solutions` |

### Дополнение из открытых источников

По пояснениям к ТЗ (п. 3.2) приоритет — дополнить ТТХ существующих решений, а новые решения добавлять ограниченно, до 5–10 на тип объекта. Команда добавила два решения для медучреждения: в каталоге организатора нет роботов для доставки лотков и тележек внутри здания с лифтами.

| Решение | Зачем | Источник |
|---|---|---|
| Pudu T300 (до 300 кг) | тележки с питанием и контейнеры с бельём | robort.ru, 26.09.2026 |
| PuduBot 2 (лотки до 10 кг) | медикаменты и пробы; ТТХ — из документа организатора | kiit.ru, 26.09.2026 |

Кроме того, беспилотный тягач Cognitive Pilot и грузовик EVOCARGO N1 из каталога организатора (сценарий «Перевозка грузов на закрытых площадках») привязаны к аэропорту — как в документе «Примеры решений».

## Загрузка и актуализация данных

1. Положить обновлённые файлы организатора в `backend/data/raw/` (`catalog_export_v4.csv`, `datasets.xlsx`).
2. При необходимости дополнить `reference_specs.json` (паспорта) и `open_sources.json` (новые решения со ссылкой и датой).
3. Запустить `python scripts/etl.py`. Скрипт пересобирает `data/seed/*.json` и печатает отчёт о полноте: сколько решений, с ценой, с грузоподъёмностью, с производительностью, сколько подтверждено. `catalog_version` — хеш исходных файлов.
4. В интерфейсе администратора нажать «Перезагрузить каталог из ETL» (или `POST /api/admin/catalog/reload`). Правки администратора сохраняются в БД, но при перезагрузке заменяются данными ETL — постоянные правки вносите в исходные файлы.
5. Сохранённые проекты хранят `catalog_version` и `model_version`. При повторном открытии расчёт пересчитывается, и платформа сообщает, совпал ли он с сохранённым.

Результат ETL на текущих данных: 223 строки каталога → 187 уникальных решений + 2 из открытых источников. У всех есть цена; грузоподъёмность — у 22, производительность — у 39, подтверждённые паспортные ТТХ — у 9. Остальные ТТХ помечены как требующие запроса вендору — это главный риск достоверности, он явно показан в интерфейсе.

## Параметры объекта

Для каждого типа объекта — свой набор параметров из датасета организатора (склад — 42, аэропорт — 39, медучреждение — 57) и 15 параметров для произвольного объекта. Параметры, участвующие в расчёте выбранной операции, помечены звёздочкой и обязательны. Проверяются тип, неотрицательность (если диапазон это предполагает) и типовой диапазон из датасета. Ошибки сформулированы с подсказкой, как исправить.

Загрузка: шаблон `.xlsx` или `.csv` (кнопка «Шаблон»), либо сам файл датасета организатора — берётся лист с названием объекта. Столбцы: Параметр | Ед. изм. | Значение.
